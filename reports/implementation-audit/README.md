# Отбор практик из готовых реализаций — 8 октября 2026

Цель: RGB-веб-камера MacBook, без внешних датчиков; минимум конфликтующих жестов, быстрый поток, фиксация точки клика/области прокрутки, два динамических свайпа, удобное возвращение руки. Статья не редактируется. Здесь фиксируется инженерный отбор для системы, а не обзор для публикации.

Исходники шести репозиториев скачаны для чтения в research/references. Точные commits, даты, SHA256 файлов и наличие LICENSE записаны в sources.json. Сторонние приложения, install.sh, checkpoint-файлы и установщики не запускались. Название «reliable» в README не считается доказательством качества: большинство проверок в этих проектах синтетические. По отсутствующим живым измерениям оценки не выдумываются.

## Собранная архитектура

1. MediaPipe Hand Landmarker через официальный Tasks API в потоке обработки. Захват и обработка отделены от Qt и OS; хранится последний кадр/результат, очередь не растёт. [Документация Google](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/python) описывает трекинг в VIDEO/LIVE_STREAM; наш синхронный VIDEO вызов расположен в отдельном worker, что сохраняет причинный порядок результатов.
2. В основном2D-профиле — aspect-corrected image geometry. Не используем нестабильную оценку физического луча для клика. Предыдущая3D-калибровка остаётся отдельным экспериментом. Ни один рассмотренный webcam-проект не подтверждает точное лазерное наведение на встроенный экран.
3. Относительный якорь медианы ладони, выбранный экран и текущий macOS-курсор; возврат руки без скачка. API совместим с прежним абсолютным режимом. Существующий time-aware фильтр соответствует принципу [1€ Filter](https://gery.casiez.net/1euro/): сглаживание в покое и меньшая задержка на быстром движении. Параметры требуют персональной проверки.
4. Один владелец команд: point / pinch / scroll / swipe. Щипок фиксирует последнюю точку до сгибания пальца; scroll не двигает курсор. В2D для scroll используется центр ладони и подвижная мёртвая зона0,006 высоты кадра. Дробные единицы не отбрасывают медленное накопленное движение. Этот порог инженерный, не результат поиска оптимума.
5. Свайп: спокойная ладонь0,16с → траектория; два направления, displacement≥0,20 ширины кадра, доминирование горизонтали2:1, окно0,12–1,2с. Пропуск≤0,15с допускается только после arming. Скачок>4 единиц кадра/с плюс0,035 запаса отменяет эпизод. Поза может стать uncertain во время движения; явные pinch/V отменяют swipe. После события нужен нейтральный интервал, короткая потеря руки не снимает блокировку повтора. Числа являются начальной конфигурацией.
6. Настройки кастомных static/dynamic жестов, TRAIN/TRIAL, личные профили и DTW остаются в расширенном режиме и не конкурируют с базовыми пятью классами. Их свободное качество на новых пользовательских записях пока не подтверждено.

## Доказательства и границы

Полный локальный запуск после изменений:242 passed16,24с. Новые регрессии воспроизводили отказ при uncertain-позе внутри свайпа, кратком пропуске, ожидании с дрожанием, скачке координат, конфликте сV/щипком, неполном сгибании безымянного, неподвижном vector-wrist при движении image-palm и дрожании колеса у порога. Это проверки алгоритма, не пользовательская accuracy.

Ранее сохранены разрешения/FPS, GUI-профилирование и сравнение абсолютного/относительного курсора в reports/pointing-v4. Профилирование не установило причину замедленного хвоста нативного сеанса. Оно не обосновывает обещание30FPS при любой сцене/нагрузке. Нужны новые живые попытки с полученными событиями окна, отдельно от распознанных команд; слово «идеальная» не заменяет эти измерения.


## Дополнительное сравнение трекеров

[Apple Vision](https://developer.apple.com/documentation/vision/detecting-hand-poses-with-vision) проверен как нативный21-точечный2D-трекер. В vision-probe/results.json — одинаковые30 последовательных кадров из первого доступного видео каждого из пяти разных person-ID IPN Hand, первые5 кадров каждого фрагмента исключены;125 измеренных кадров на backend, порядок вызовов чередуется. Камера/OS/GUI не использованы; PNG/JPEG не перекодируются. По фактическому payload source-frame форматы фиксируются в measurements. MLP у MediaPipe выключен для выделения извлечения точек.

| Измерение на публичных кадрах | MediaPipe | Apple Vision |
|---|---:|---:|
| Обработка маршрута p50/p95, мс |11,81 /24,29|6,30 /7,53|
| Наблюдения с найденной рукой |90 /125|100 /125|
| Все21 точки с Apple confidence≥0,4 |API не возвращает сопоставимых confidence|89 /125|

Число найденных рук не является recall без разметки присутствия/суставов. Confidence разных API не сопоставимы. MediaPipe VIDEO использует временной трекинг, Vision здесь — запросы отдельных изображений. Измерения включают конверсию пикселей/извлечение точек, но не чтение видео. Это малый набор, не весь IPN Hand. Исходные файлы/кадры и модель зафиксированы в JSON, сохранены числовые points и timings.csv.

Проверен отдельный нативный поток камеры с новым Vision-адаптером:1920×1080,302 пакета за10,00с после20 прогревочных,30,09FPS. Обработка p50/p95=24,82/28,20мс; возраст числового результата25,18/28,64мс. Рука отсутствовала во всех кадрах. Большое разрешение/другая сцена показали более медленную обработку, чем малые публичные кадры. Не делаем вывод, что Vision всегда быстрее MediaPipe: живого одновременного A/B и ground truth нет. Детали — vision-probe/live-camera.json; это не photon-to-GUI/OS задержка.

Вывод для продукта: добавить переключаемый Apple Vision2D, оставить MediaPipe доступным. Vision-адаптер требует все21 конечные точки с confidence≥0,4; неполные данные дают отсутствие руки. Глубина не выдумывается, поэтому3D-режим с ним запрещён. Смена backend останавливает поток/ввод и создаёт новый контекст; она записывается в метаданные сеанса. Личные шаблоны надо независимо проверять после смены модели. На этой машине установлены официальные PyObjC Vision/CoreML12.2.2; зависимости добавлены условно для macOS.

Также изучен [WiLoR для Apple Silicon](https://github.com/lyonsno/wilor-mlx): реконструкция MANO/3D, но более тяжёлые веса и отдельные условия MANO. Авторские измерения относятся кM4Max, а не к нашему M2Pro; физическое экранное наведение ими не подтверждается. Этот вариант не добавляется в базовый режим минимальной задержки без отдельной проверки качества/ресурсов.
